Каждый этап вы уже видели по отдельности. Сегодня — вместе.

Зачем вообще CI

  • Код проверяется на каждый пуш, а не «когда вспомнили»
  • Проверки одинаковые для всех — не зависят от машины разработчика
  • Ошибка найдена через 2 минуты после пуша, а не на проде
  • Пайплайн — это тот же скрипт, что вы гоняете локально

Поэтому занятие 1 начинается с локального прогона: CI не должен делать ничего, чего вы не можете сделать руками.

GitHub Actions: анатомия workflow

on:          # когда запускать (push, тег, расписание)
permissions: # что можно токену прогона (packages: write!)
jobs:
  lint-test:
    runs-on: ubuntu-latest  # где выполнять
    steps:                  # что делать
      - uses: actions/checkout@v4   # готовый action
      - run: pytest app/tests -v    # или своя команда

needs связывает джобы в цепочку: упала первая — дальше не идём.

Образ = артефакт сборки

  • Собираем образ один раз — в CI
  • Тег — хэш коммита: всегда понятно, из какого кода образ
  • latest — удобный указатель, но не для отката
  • Дальше по цепочке едет именно этот бит — без пересборок

«У меня локально собирается» — антипаттерн. Образ из CI — единственный источник правды.

Trivy: уязвимости в образе

  • CVE — публично известная уязвимость в пакете
  • Severity: LOW → MEDIUM → HIGH → CRITICAL
  • Базовый образ python:3.8-slim — десятки CVE, поддержка прекращена
  • Trivy сканирует образ за секунды и умеет ронять пайплайн: exit-code: 1

Уязвимый образ не должен доезжать до реестра.

Подавлять находки можно — но осознанно: .trivyignore с обоснованием (занятие 2, задание 3).

GHCR: где живут образы

  • GitHub Container Registry — реестр образов рядом с кодом
  • Бесплатен, авторизация через GITHUB_TOKEN — ничего заводить не надо
  • Образ привязан к репозиторию: ghcr.io/<логин>/<репо>:<тег>
  • Имя — только строчными буквами

GHCR — наш «внешний мир». А дальше образы должен раздавать Artifactory.

  • Полный аудит: кто, что и когда скачал

Staging → release: promotion

docker-staging-local
«проверяем»
→
jf rt docker-promote
→
docker-release-local
«можно в прод»
  • В release попадает только то, что прошло проверки
  • Promotion — это копирование проверенного артефакта, а не новая сборка
  • Деплой смотрит только в release-репозиторий

Деплой без Kubernetes

services:
  app:
    image: localhost:8092/pipeline-lab:1.0.0  # release-репозиторий
    ports: ["8080:8000"]
  • docker compose pull && up -d — весь деплой
  • Smoke-проверка: curl /health после подъёма
  • Откат = поменять тег на предыдущий и поднять заново — секунды

В бою здесь был бы Kubernetes или Ansible — принцип тот же: pull из реестра, не сборка на сервере.

Откат

  • Старые версии уже лежат в реестре — ничего пересобирать не надо
  • Откат: тег назад → compose up -d → проверка версии
  • Поэтому теги образов должны быть осмысленными: хэш коммита или семвер, а не только latest

Время отката — главная метрика зрелости пайплайна. Отрабатываем в задании 7.

Jenkins — альтернатива

  • Тот же пайплайн можно записать на Jenkins — см. jenkins-demo/Jenkinsfile
  • Концепции те же: stage ≈ job, agent ≈ runs-on, credentials ≈ secrets
  • В конце занятия 1 — короткий живой показ

Итоги

  • Пайплайн = проверки + сканер + реестр + деплой, одной цепочкой
  • Уязвимый образ не доезжает до реестра — Trivy роняет сборку
  • Прод ходит только в Artifactory, в прод едет только release
  • Откат — это старый тег, а не новая сборка
